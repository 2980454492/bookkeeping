## 审查清单

只检查注释，不检查代码逻辑、安全、性能。按 CLIADE.md 注释规范逐项检查当前变更：

### 底线项（缺了就是未完成）

- [ ] 新增文件有文件头：`// filename.xxx — 一句话职责`，需说明"这个模块负责什么、谁在调用它"
- [ ] 新增函数/方法有注释：用途 + 关键参数含义（一行够用，不求长文）
- [ ] 新增类/结构体有注释：代表什么实体、被哪些模块使用
- [ ] 关键设计决策旁有"为什么"注释：为什么选这个值、这个顺序、这个方案

### 质量项（写得好不好）

- [ ] "为什么"优先：注释回答的是动机和约束，不是复述代码
- [ ] 无废话：没有 `i++; // i 自增`、`int port = 18080; // 设置端口` 之类
- [ ] 无过期注释：修改代码后，旁边注释已同步更新
- [ ] 段落分隔清晰：长文件有 `// ── 段落名 ──` 视觉分隔

### 禁止项（有就该删）

- [ ] 无被注释掉的代码块（git 里有历史，用不着留尸）
- [ ] 无函数体内的 `/* */`（统一用 `//`）
- [ ] 无"TODO 以后改"（要么现在就做，要么删掉）

---

## 输出格式

只报问题，不报通过项。按关注度排序：

| 级别 | 含义 | 示例 |
|------|------|------|
| 🔴 缺失 | 底线项不满足，应补齐再提交 | 新文件缺文件头、新函数无注释 |
| 🟡 冗余 | 有注释但没价值 / 过期 / 和代码不一致 | 废话注释、修改代码未更新注释 |
| 🔵 建议 | 可以更好 | 关键逻辑缺少"为什么"、段落太长缺分隔线 |

每个问题附：**文件:行号** + **问题描述** + **修复建议（一句话）**。

示例：
```
🔴 [缺失] handlers.cpp:345 — 新增函数 exportToJson 没有注释
  修复：添加 /** 将记录导出为 JSON 文件 */ 或一行 // 说明用途和参数

🟡 [冗余] db.cpp:200 — `port = 18080; // 设置端口为 18080` 纯复述代码
  修复：改为 `// 与 run.sh / README 保持一致`

🔵 [建议] app.js:420-480 — renderStats() 60 行无段落分隔
  修复：按「数据准备／DOM 渲染／事件绑定」用 // ── 分成三段
```
